# Ранбук: от темы до опубликованного поста

> Операторский порядок конвейера. Точка входа - скилл `/post`.
> Два обязательных согласования с человеком: **тип и фактура** до генерации,
> **финальный текст** до публикации. Всё между ними агент делает сам.

## Шаг 0 · Долги по факту

```bash
python scripts/check-facts.py
```

Есть незакрытые долги по прошлым постам - сначала закрыть их. Без факта прошлого
поста калибровать нечего, и конвейер начинает выдумывать вместо того, чтобы учиться.

## Шаг 1 · Тип и папка

Определить **тип поста** из трёх ([POST-TYPES.md](POST-TYPES.md)):
дайджест · обновление и фича · кейс и статья.

Для обновления сразу выбрать **вариант карусели**: «что изменилось» (карточки
изменений) или «как сделать» (карточки шагов). От этого зависит текст: во втором
случае шаги в тексте не пересказываются, а обещаются одной строкой.

Завести `content/posts/<YYYY-MM-DD>-<slug>/` с файлами `post.md` и `ab-plan.json`.

Свериться с `content/plan.md`: какие типы и зоны продукта заняты последними тремя
постами (антиповторы, [CONTENT-PLAN.md §3](CONTENT-PLAN.md)).

## Шаг 2 · Фактура ⛔ гейт качества

**Единственный допустимый источник продуктовых утверждений - база знаний Кайтена**
`faq-ru.kaiten.site` и материалы блога. Не память агента, не пресс-релиз, не догадка.

Из статьи базы знаний выписываются **дословно**:

- названия разделов, вкладок, кнопок, полей, переключателей;
- порядок действий пользователя;
- ограничения: тариф, модуль, версия серверной поставки, статус беты;
- даты отключения старой функциональности.

Всё это кладётся в `post.md` в раздел «Фактура» со ссылкой на источник.
**Утверждение без источника в пост не идёт.** Чего в статье нет, того нет в посте:
если про API не написано, про API не пишем.

Отдельным списком фиксируется **«чего на странице нет»** - чтобы соблазн дописать
по памяти был виден.

Для кейса фактура другая: согласие героя на имя, должность и название компании,
цифры масштаба, ссылка на полный материал.

## Шаг 3 · Угол и роль

Кому это нужно и что человек сможет сделать после прочтения, чего не мог до.
Роль и боль берутся дословно из [../references/icp-kaiten.md](../references/icp-kaiten.md).

Дать 1-3 варианта угла с обоснованием, проверить по `content/plan.md`, что угол
не повторяет последние посты.

## Шаг 4 · ⛔ ГЕЙТ: согласование типа, фактуры и угла

Человек выбирает или правит. Генерация только после «ок».

## Шаг 5 · Текст

Скелет типа берётся из [POST-TYPES.md](POST-TYPES.md) и соблюдается.
Язык - по [../references/editorial-policy.md](../references/editorial-policy.md).
Оформление - по [../references/voice-profile.md](../references/voice-profile.md).

Вариантов имеет смысл делать **2-3, и только внутри одного типа**: разный заход,
разная длина, разная концовка. Пять разножанровых текстов на одну тему конвейеру
своего канала не нужны, тип уже выбран на шаге 4.

Тексты кладутся в `post.md` в блоки:

````
## Вариант 1 · обновление
```post
<текст поста>
```
````

Название типа в заголовке раздела обязательно: по нему валидатор включает проверки типа.

## Шаг 6 · ⛔ ВАЛИДАТОР (автономно)

```bash
python scripts/validate-post.py content/posts/<slug>/post.md
```

Любой FAIL правится, валидатор запускается снова, пока не будет 0.

Валидатор ловит механику: буква «ё», запрещённая лексика, оценочные усилители,
нейро-шлак, неверное позиционирование, тире и дефисы, «Вы» с прописной, точка
в заголовке, обязательные элементы типа, глубина продукта, ссылка, клоны в наборе.

⚠️ Если валидатор ругается на текст, который человек правил руками, не перезаписывать
молча: показать нарушения и спросить.

**Чего валидатор не умеет и что проверяется рассуждением:**

- каждое ли продуктовое утверждение подтверждено статьёй базы знаний;
- совпадают ли названия кнопок и полей с инструкцией дословно;
- пассивный залог, инверсия, модальные глаголы;
- польза каждого абзаца («как это поможет читателю?»);
- честность оговорок: указаны ли тариф, модуль, версия, статус беты;
- ICP-сверка: роль и боль дословно из `icp-kaiten.md`.

## Шаг 7 · Редакционная проверка

По [SCORING.md](SCORING.md): разметка утверждений FACT/INFERENCE/RISK, проверка каждого
FACT по базе знаний, шесть линз с весами, зона решения, панель персон, правки P0/P1.
Отчёт складывается в `content/posts/<slug>/scoring/`.

## Шаг 8 · Рекомендация

Явно: **какой вариант ставим и почему**. Не «победитель по баллам», а «на этой неделе
нужен этот, потому что прошлый пост был дайджестом по той же зоне продукта».

## Шаг 9 · ⛔ ГЕЙТ: согласование финального текста

Человек читает победителя с правками P0 и говорит «ок» или правит.

## Шаг 10 · Иллюстрации и предсказание

Формат берётся по типу поста из [VISUALS.md](VISUALS.md): обложка и карусель.
Для обновления карусель бывает двух видов: карточки изменений или карточки шагов.
Число карточек в карусели обязано совпадать с числом, обещанным в тексте и на обложке.

```bash
node scripts/render-images.mjs content/posts/<slug>/img/*.html
python scripts/render-images.py content/posts/<slug>/img/*.html   # если Node нет
```

**Проверить глазами: на макетах нет буквы «ё», имя бренда латиницей, конфиденциальное
заблюрено, скриншот читается без увеличения.**

Заполнить `ab-plan.json`: `predictions.per100`, целевые роли, гипотезы, риски, UTM
в формате канала `utm_source=tg&utm_medium=social&utm_campaign=<ДДММ>`.
**Предсказание заводится ДО публикации**, иначе калибровать будет нечего.

## Шаг 10½ · Передача в работу

После согласования собрать **`PUBLISH.md`** в папке поста. Это единственный файл,
который открывает тот, кто публикует: в `post.md` лежат фактура, отклонённые
варианты и скоринг, разбираться в них публикатору незачем.

В `PUBLISH.md` входит:

1. **Чистый текст** победителя в блоке для копирования, без правок и комментариев.
2. **Разметка для Телеграма:** что жирным, что цитатой, на какое слово вешать ссылку.
3. **Готовый URL с меткой** `utm_campaign` и напоминание поменять дату, если публикация
   съедет.
4. **Какую картинку ставить** и есть ли альтернатива (гифка, карусель).
5. **Чек-лист «проверить до публикации»** со всем, что агент проверить не смог:
   сроки, доступность функции, работоспособность ссылки.
6. **Что сделать после выхода:** проставить `published_at`, снять факт T+24 и T+72.

Текст берётся из `post.md` **скриптом**, а не переписывается руками: при копипасте
теряются переносы и кавычки, и согласованная версия расходится с опубликованной.

```bash
python scripts/extract-variant.py content/posts/<slug>/post.md       # список вариантов
python scripts/extract-variant.py content/posts/<slug>/post.md 1     # текст с проверкой
```

Скрипт заодно ловит то, что чаще всего ломается при переносе: букву «ё», прямые
кавычки, дефис вместо длинного тире и голый URL.

## Шаг 11 · Публикация и факт

После выхода проставить `published_at`. Дальше ритуал [FACT-LOOP.md](FACT-LOOP.md):
T+24 (просмотры, реакции, пересылки, комментарии, отписки), T+72 (плюс клики)
→ `facts` → калибровка против предсказаний → уроки в `lessons`.
**Предсказания задним числом не переписываются.**

Обновить `content/plan.md`, таблицу «Что вышло»: тип, зона продукта, угол, композиция обложки.

Если пост показал приём, которого ещё нет в корпусе, добавить его в
[../references/real-posts.md](../references/real-posts.md).

## Definition of Done

Долги закрыты · тип выбран · фактура из базы знаний с дословными названиями и списком
«чего нет» · угол согласован · текст по скелету типа · **валидатор = 0** · редакционная
проверка с разметкой утверждений · рекомендация · финальный текст согласован ·
иллюстрации по формату типа отрендерены и просмотрены глазами · ab-plan с предсказанием
заполнен ДО публикации · план обновлён · после выхода факт и калибровка.
